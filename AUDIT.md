## Findings

### CRITICAL

- [x] **`AdvancedClassSystem.Update` calls `fmt.Sprintf("%d", entity.ID)` per entity per frame** — `pkg/engine/advanced_class_system.go:32` — Every call to `AdvancedClassSystem.Update` iterates all entities; for each entity with an `"advanced_class"` component it executes `fmt.Sprintf("%d", entity.ID)`, which heap-allocates a string and calls into the `fmt` reflection machinery. With 50 player/NPC entities at 60 FPS this is **3,000+ string allocations per second** producing ~48 KB/s of GC pressure from a single system. The string is used only as a map key inside `advanced.Manager`. **Remediation:** Use `strconv.AppendUint(key[:0], entity.ID, 10)` with a fixed-size stack buffer, or key the `Manager` maps by `uint64` directly. Drop the string conversion entirely:
  ```go
  // Replace: playerID := fmt.Sprintf("%d", entity.ID)
  // With:    playerID := strconv.FormatUint(entity.ID, 10)
  // Better:  key the manager maps by uint64 to eliminate string conversion
  ```

- [x] **`AISystem.Update` uses uncached `GetComponent("ai")` map lookup on every entity every frame** — `pkg/engine/ai_system.go:82` — The `Update` loop calls `entity.GetComponent("ai")` (a `map[string]Component` lookup) for every entity in the world, not just AI entities. With 500 entities this is 30,000 map lookups/sec. 17 other component types are fast-path cached (e.g. `GetPosition()`, `GetTeam()`), but `"ai"` is not. The AI system also calls `GetComponent("attack")`, `GetComponent("animation")`, and `GetComponent("aim")` inside the hot decision path (11 total uncached lookups). **Remediation:** (1) Pre-filter with `world.GetEntitiesWith("ai")` at start of `Update`, or (2) add `"ai"` to the entity hot-path cache in `ecs.go`. Option 1 is immediate and uses the existing query-cache infrastructure.

### HIGH

- [x] **`MovementSystem` `visitedCells` map-of-maps — per-entity inner map allocated lazily in `Update` hot path** — `pkg/engine/movement.go:286-292` — `trackAreaVisit` is called every frame for every moving entity. The first time an entity enters a new cell, `s.visitedCells[entity.ID] == nil` triggers `make(map[int64]bool)` inside the hot path. With many entities this creates per-entity GC pressure. More critically, `s.visitedCells` (type `map[uint64]map[int64]bool`) is never cleaned up for dead/removed entities, growing without bound over a long session. **Remediation:** Store `visitedCells` as a flat `map[uint64]map[int64]struct{}` (saves one byte per entry), pre-create the inner map in `trackAreaVisit` with a reasonable initial size, and hook entity removal to call `ClearVisitedCells`. Consider replacing with a bitset-over-grid for fixed memory usage.

- [x] **`GetEntitiesWith` query cache invalidated on every entity add/remove, forcing O(n × q) linear rescan** — `pkg/engine/ecs.go:860-862` — `invalidateQueryCache` marks **all** cached queries dirty on every entity addition or removal. Each dirtied query is then rebuilt lazily (O(n) scan with `entityHasAllComponents`) on the next call. In an 8-player server where NPCs spawn/despawn frequently, this repeatedly invalidates 100+ distinct cached queries simultaneously, causing cascading O(n) rescans that each touch `cachedEntityList`. **Remediation:** Track which component types each query depends on, and only invalidate queries whose component set intersects the added/removed entity's components. This reduces cascading invalidation from O(q) to O(1) in the common case.

- [x] **`GenerateGradient` allocates one `color.RGBA` per pixel on the heap (65,538 allocs/op for a 256×256 image)** — `pkg/rendering/palette/gradient.go:66,214` — `interpolateColors` returns `color.Color` (interface), causing `color.RGBA` (8 bytes) to escape to the heap on every `img.Set(x, y, c)` call. For a 256×256 gradient this is 65,536 heap objects per call. While `GenerateGradient` is not called per-frame in the main game loop, it is invoked on zone transition and during pre-warming. **Remediation:** Change `img.Set(x, y, c)` to direct `img.Pix` array writes using a helper that computes r/g/b/a and writes them as four bytes, bypassing interface boxing entirely. Alternatively, make `interpolateColors` return `color.RGBA` directly (a concrete type, not interface).

- [x] **`TerrainCache.Get` copies the entire `*Terrain` result slice on every warm hit (55 allocs, 33 KB per call)** — `pkg/procgen/terrain/cache.go` — `BenchmarkTerrainCache_Get` shows **55 allocs / 33,540 B** even on a warm cache hit. This suggests the cache is doing a deep-copy or JSON round-trip of the terrain on every read. `TerrainCache` returns `*Terrain` (a pointer), so the per-call alloc cost should be minimal if the cache simply returns the stored pointer. Investigate whether `LRU eviction` or internal deserialization is triggering copies. **Remediation:** Confirm the cache returns a pointer without copying; if the `gob` path is being taken for in-memory hits, fix the read path to bypass `gob` and return the cached `*Terrain` directly.

- [x] **`SpatialVoiceSystem.Update` calls `entity.HasComponent("spatial_voice")` + `entity.GetComponent("spatial_voice")` for every entity** — `pkg/engine/spatial_voice_system.go:61-73` — Two consecutive map lookups (`HasComponent` then `GetComponent`) per entity per frame. Since `"spatial_voice"` is not in the fast-path cache, both are `map[string]Component` accesses. **Remediation:** Replace with `world.GetEntitiesWith("spatial_voice", "position")` before the loop; `HasComponent`+`GetComponent` double-tap disappears.

### MEDIUM

- [x] **`GenerateCacheKey` uses `crypto/sha256` and `fmt.Sprintf` (6 allocs, 682 ns/call)** — `pkg/procgen/terrain/cache.go:101-136` — Terrain cache key generation uses `crypto/sha256` (correct for collision resistance) but also calls `fmt.Sprintf("%v", params.Custom[k])` for each custom parameter, allocating strings. 682 ns × cache misses is fine for on-demand terrain generation, but during `PrewarmCache` (153,333 allocs) it amplifies. **Remediation:** Pre-allocate a `[]byte` scratch buffer using a `sync.Pool`-backed hasher (similar to the sprite cache's `hasherPool`); replace `fmt.Sprintf` with `strconv` where possible.

- [x] **`CellularGenerator.Generate` produces 4,081 allocs / 554 KB per invocation despite double-buffer pattern** — `pkg/procgen/terrain/cellular.go` — The pre-allocated `bufferA`/`bufferB` double-buffer is good, but 4,081 allocs still remain (possibly from flood-fill, room construction, or per-tile `logrus.WithFields` calls at debug level). This is cold-path but shows that the double-buffer optimization is only partially effective. **Remediation:** Profile with `go test -cpuprofile`; likely flood-fill queue growth (`[]point` appends) or neighbor-offset slice recreations are the remaining sources.

- [x] **`AdvancedClassSystem.Update` performs uncached `GetComponent("advanced_class")` per entity per frame** — `pkg/engine/advanced_class_system.go:27` — In addition to the `fmt.Sprintf` issue (CRITICAL-1), the system uses uncached `entity.GetComponent("advanced_class")` for every entity on every frame. This is a second map lookup per entity on top of the string allocation. **Remediation:** Pre-filter using `world.GetEntitiesWith("advanced_class")` or add `"advanced_class"` to the cached component type set in `ecs.go`.

- [x] **226 unguarded `logrus.WithFields`/`WithField` calls in `pkg/engine` non-test non-AI code** — various files — The AI and movement systems have cached debug flags (`aiDebugEnabled`, `movementDebugEnabled`) that skip `WithFields` when debug is off. Most other systems (achievement, adaptive soundtrack, advanced class UI, animation) call `logrus.WithFields` unconditionally, allocating a `logrus.Fields` map even when the log level means nothing is written. At 60 FPS × N systems this is sustained GC pressure. **Remediation:** Adopt the same `if debugEnabled { logrus.WithFields... }` pattern already used in `ai_system.go` and `movement.go` for all hot-path systems.

- [x] **`interpolateColors` returns `color.Color` interface causing heap escape on every pixel in `GenerateGradient`** — `pkg/rendering/palette/gradient.go:174` — The concrete return type `color.RGBA` cannot be returned without boxing when the function signature returns the interface `color.Color`. This is the root cause of the 65,538-alloc finding. **Remediation:** Change `interpolateColors` signature to `func interpolateColors(colors []color.Color, t float64) color.RGBA` and update `GenerateGradient` to call `img.SetRGBA(x, y, c)` (if available) or write directly to `img.Pix`.

- [x] **`GetAudibleEntities` in `SpatialVoiceSystem` creates `make([]*Entity, 0)` without capacity every call** — `pkg/engine/spatial_voice_system.go:250` — Called from voice-processing code (not the 60 FPS game loop, but potentially at voice-packet rate). **Remediation:** Pre-allocate with `make([]*Entity, 0, 16)` or use a reused buffer field.

### LOW

- [x] **`TerrainCache` uses `sort.Strings(keys)` + per-key `fmt.Sprintf` on custom params in `GenerateCacheKey`** — `pkg/procgen/terrain/cache.go:127-133` — Allocates a key slice and sorts it on every cache-key computation even when `Custom` is nil or small. Already partly explained above (MEDIUM-3); the `sort.Strings` itself is cold-path overhead when called only at terrain generation time. **Remediation:** Merge with the hasher-pool fix in MEDIUM-3.

- [x] **`pkg/engine` has 1,606 non-test `GetComponent` calls that bypass the hot-path cache** — scattered across system files — Many systems access infrequently-used but per-entity components (e.g. `"mana"`, `"pvp_rating"`, `"matchmaking"`, `"merchantcaravan"`) via map lookup. These are correct uses of the generic accessor (components too rare to cache), but a few appear inside `Update` loops. **Remediation:** Audit `Update` methods calling `GetComponent` for components that could be cached or pre-filtered; add to hot-path cache only when the component type appears in every-frame loops with ≥10 entity expectation.

- [x] **`BenchmarkAdaptiveComposer_GenerateTrack` — 1.84 MB / 15 allocs per track** — `pkg/audio/music` — One-shot generation, not per-frame. However, regenerating the track on every `Update` call (even with the 66 ns fast path) would be catastrophic. Confirm `AdaptiveComposer.Update` is the fast path and `GenerateTrack` is called only when needed. Current benchmark confirms 66 ns zero-alloc `Update`. **Remediation:** None required — behavior is correct. Add documentation comment to `GenerateTrack` noting the 1.84 MB cost.

- [x] **No per-system frame-budget enforcement in `World.Update`** — `pkg/engine/ecs.go:700-708` — `PerformanceMetrics.RecordSystemTime` records timings but there is no mechanism to warn or throttle a misbehaving system that exceeds its frame budget. A single slow system silently blows the 16.6 ms frame window. **Remediation:** Add a configurable per-system budget (e.g. 2 ms default) and emit a `logrus.Warn` (rate-limited) when a system exceeds it.

- [ ] **`InitializeGameSystems` is a 1,940-line function with complexity 31.9** — `pkg/engine/system_init.go:1` — The `go-stats-generator` flagged this as the most complex function in the codebase. While it is initialization code (not per-frame), its length makes it difficult to verify that the integration chain (Definition → Instantiation → Registration) is complete and correct. **Remediation:** Split into domain-specific `initXxxSystems()` helpers (collision, AI, rendering, audio, etc.) and call them from `InitializeGameSystems`.

## False Positives Considered and Rejected

| Candidate Finding | Reason Rejected |
|-------------------|----------------|
| `World.Update` calls `time.Now()` per system | Intentional: per-system timing for `PerformanceMetrics`. Single call per system (not per entity). Unavoidable for accurate per-system instrumentation. |
| `Quadtree.Query` allocates output slice | `QueryInto` zero-alloc path exists and is used by AI and collision systems. `Query` is only used in tests. |
| Sprite `BatchGenerate` spawns goroutines | Worker count is bounded by `MaxWorkers` (default 4), WaitGroup-synchronized. Not unbounded. |
| `game.go` spawns 15 goroutines in `initializeUIComponents` | Called once at startup with `sync.WaitGroup`; not per-frame. Intentional parallel initialization. |
| `sort.Slice` in `EbitenRenderSystem.sortEntitiesByLayer` | Uses `slices.SortFunc` (generic, inlineable) on a pre-allocated `sortCacheBuffer` that caches Y positions. Y-sort is necessary for correct depth ordering. |
| `GetEntitiesWith` query cache returns cached slice | Correct — cache hit returns existing slice pointer (0 allocs). Cache miss copies queryBuffer to own backing array (unavoidable for cache safety). |
| `TerrainCache` uses `sync.RWMutex` | Correct for concurrent terrain generation and read. Not in game-loop hot path. |
| `logrus.WithFields` in 226 locations | Partially valid — see MEDIUM-4. AI/movement systems correctly guard behind cached flags. The 226 count includes systems that run infrequently (achievement, guild, economy). Only systems that run every frame with large entity sets are impactful. |
| `CityEvolutionSystem.GetCitiesInState` uses `make([]*Entity, 0)` | Not called from `Update` — it is a query API. Not per-frame. |
| `MerchantCaravanSystem.GetCaravansAtServer` uses `make([]*Entity, 0)` | Query API, not called from `Update`. |
| Cellular automata 4,081 allocs | Cold path — terrain generation on zone load, not per-frame. The absolute count (4,081) is not blocking the 60 FPS target. |
| `sha256` in `GenerateCacheKey` | Cold path, invoked at zone transition. 682 ns is acceptable for cache key generation that happens ≤once per zone. |
| `AdaptiveComposer.GenerateTrack` 1.84 MB | Cold path, not called from `Update`. `Update` itself is zero-alloc. |
